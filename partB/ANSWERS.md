# Part B — Capacity reconciliation

All numbers below are generated by `capacity_calc.py` in this folder — run it yourself:
`python3 capacity_calc.py` (reads `model_spec.md`'s numbers, hardcoded at the top of the
script with their source noted, and `bench_log.csv` directly).

## B1 — KV-cache bytes/token and max concurrent 4096-token sequences

**Arithmetic (dense attention, GQA with 8 KV heads, fp16 weights and KV cache):**

```
KV bytes/token = 2 (K and V) × 28 layers × 8 KV heads × 128 head_dim × 2 bytes (fp16)
               = 114,688 bytes/token  (112.0 KiB/token)
```

Usable memory for the KV cache, subtracting model weights and the stated non-KV overhead
from the memory the serving config is allowed to touch:

```
24 GB × 0.92 (gpu_memory_utilization)
  − 8.40 GB (weights: 4.2B params × 2 bytes fp16)
  − 1.60 GB (non-KV runtime overhead, as stated in model_spec.md)
  = 12.08 GB usable for KV cache
```

```
KV cache for one full 4096-token sequence = 4096 × 114,688 bytes = 469,762,048 bytes (0.470 GB)
Max concurrent 4096-token sequences ≈ 12.08 GB / 0.470 GB ≈ 25.7  →  ~25 sequences
```

**Caveat:** this reads "24 GB" and "4.2 B params × 2 bytes" as decimal GB throughout. If those
are meant as binary GiB instead, the ceiling moves to ~29 sequences — a ~14% swing on the
exact number, though it doesn't change which conclusion below it supports. Worth confirming
with whoever wrote model_spec.md before this number goes into a capacity-planning doc.

**Check against the log:** batch 24 (prompt_len 3584, i.e. sequences near the 4096 max
length once generation is included) runs with `kv_cache_util=0.93` and `preempted_seqs=0` —
it fits. Batch 32 already shows `kv_cache_util=0.97` and `preempted_seqs=7` — it doesn't. A
ceiling of ~25–26 concurrent full-length sequences is exactly where the log's own behavior
changes character, which is independent confirmation of the arithmetic above.

## B2 — The throughput anomaly in the prompt=3584 sweep

| batch | reported_tok_s | kv_cache_util | preempted_seqs |
|---|---|---|---|
| 4  | 565.4  | 0.16 | 0 |
| 8  | 902.6  | 0.31 | 0 |
| 16 | 1311.4 | 0.62 | 0 |
| 24 | **1607.4 (peak)** | 0.93 | 0 |
| 32 | 1384.0 (drops) | 0.97 | 7 |
| 48 | 1298.5 (drops further) | 0.97 | 23 |

Naive "throughput scales with batch" predicts batch 32 and 48 should beat batch 24. They
don't — `reported_tok_s` *falls* as batch size keeps rising past 24, even though more
requests are in flight.

**Mechanism:** batch 24 is right at the KV-cache ceiling derived in B1 (~25 sequences of
this length). Past that point, the scheduler can't hold every sequence's KV cache in GPU
memory simultaneously, so it starts preempting sequences (evicting them and later
recomputing their prefill/decode state) — `preempted_seqs` jumps from 0 to 7 to 23 in lockstep
with the throughput drop, and `kv_cache_util` pins at 0.97 (essentially full) for both rows.
Preemption-and-recompute is pure waste — cycles spent re-deriving state that had already
been computed once — so realized throughput falls even as offered load rises. This is
scheduler thrashing, not a GPU compute limit.

**Proposed change, with a predicted effect:** cap admitted concurrency (`max_num_seqs` or
equivalent) at ~24 for this prompt-length regime, rather than letting the scheduler accept
and then preempt. Predicted effect: batch-32/48-*offered* traffic held at an admitted
concurrency of 24 should sustain ~1600 tok/s (this sweep's actual ceiling) instead of
degrading to 1298 tok/s, at the cost of some requests queueing rather than running
immediately. A structural alternative with a larger predicted upside: move the KV cache to
fp8 (halving its 114,688 bytes/token footprint) to push the ceiling to roughly 50
concurrent sequences, which — if throughput continued climbing the way batch 16→24 did in
this log — could plausibly reach the ~2400–2800 tok/s range around batch 48, though that's
an extrapolation past what this log directly shows and should be measured, not assumed.

## B3 — The metric misread behind both of REPORT_v0's Section-2 conclusions

**What `reported_tok_s` actually is.** Tested the hypothesis that it counts *all* tokens
processed (prompt + generated) rather than just generated tokens:

```
reported_tok_s ≟ (prompt_len + gen_len) × num_requests / wall_clock_s
```

This matches **every row in bench_log.csv exactly** (see the script's B3 table — 13/13 rows
match to within rounding). Confirmed, not assumed.

This is the single misreading behind both of REPORT_v0's claims. Prefill (processing the
prompt) happens in one parallel forward pass and is nothing like the token-by-token decode
loop that actually determines how fast a user sees new output. Folding prefill tokens into
"throughput" makes any row with a long prompt look enormously faster than it decodes,
which is why "long prompts → better throughput" appeared in Section 2 — it's an artifact of
what's being counted, not a property of the serving stack.

**Honest goodput of the batch-24, prompt-3584 row — two independent derivations:**

1. *Generated tokens only, over wall clock:* 512 gen_len × 24 requests / 61.16 s ≈ **200.9
   tok/s**.
2. *From inter-token latency:* `itl_ms_p50` = 96.07 ms → 1000/96.07 ≈ 10.41 tok/s per
   sequence; 24 sequences decoding concurrently → 10.41 × 24 ≈ **249.8 tok/s**.

Both land in the 200–250 tok/s range — nowhere near the reported 1607.4 tok/s (a 6.4–8.0×
overstatement depending on method; the two methods disagree with each other by ~25%
because method 1's denominator includes prefill wall-clock time while method 2 measures the
decode phase only — worth noting as its own caveat rather than picking whichever number is
more convenient).

**What the report should have said:** `reported_tok_s` measures aggregate token-processing
throughput including prefill, not generation speed, and is not the right number for
capacity planning around user-facing decode latency. The batch-24/prompt-3584
configuration's actual generation throughput is ~200–250 tok/s, not 1607 tok/s. It should
not have extrapolated linearly to batch 48 (~3200 tok/s) on this basis — quite apart from
the metric being wrong, B2 shows batch 48 is a *worse* operating point than batch 24, not a
better one, because of preemption thrashing past the KV-cache ceiling.

## B4 — Metric to confirm the B2 mechanism in production

Pull the serving stack's preemption counter directly (e.g. vLLM exposes
`vllm:num_preemptions_total` as a Prometheus counter) alongside `gpu_cache_usage_perc`
(KV-cache block utilization). Expectation: both should be flat near zero up through
batch ~24-25 admitted concurrency for this prompt length, then rise sharply exactly where
KV-cache utilization crosses ~0.95–0.97 — mirroring `preempted_seqs` already visible in
`bench_log.csv` (0 → 7 → 23 across batch 24 → 32 → 48). If the preemption counter instead
stays flat while throughput still drops, the mechanism in B2 would be wrong and the real
cause would need to be something else (e.g. a compute-bound ceiling rather than a
memory/scheduling one) — this counter is the discriminating test between those two
explanations.
